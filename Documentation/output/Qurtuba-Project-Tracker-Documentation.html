01 — نظرة عامة على النظام

Qurtuba Project Tracker · System Overview

الإصدار 1.0.0 · 2026-07-05 · Quantum Dev Team

1. فكرة النظام

Qurtuba Project Tracker هو نظام ويب مؤسسي لإدارة المشاريع والمهام، يعمل بالكامل عبر لوحة تحكم إدارية حديثة (Filament 3) على المسار /admin. يتيح النظام إنشاء المشاريع وتقسيمها إلى مهام، وتوزيع هذه المهام على الأقسام والموظفين، ومتابعة التقدّم والتأخير والعوائق، وإصدار تقارير قابلة للطباعة والتصدير — كل ذلك بواجهة عربية كاملة (RTL).

النظام مطبَّق فعليًا على مشروع «تشغيل مباني قرطبة» (مدارس غراس الأخلاق الأهلية)، لكنه مصمَّم كـ منتج عام قابل لإعادة البيع والاستخدام: الهوية البصرية (اسم النظام، الشعار، اللون، نمط السايد بار) قابلة للتغيير بالكامل من داخل النظام دون لمس الكود.

2. أهداف النظام

  1. مركزية إدارة المشاريع: مصدر واحد للحقيقة لكل المشاريع والمهام وحالتها.
  2. المساءلة والشفافية: ربط كل مهمة بمسؤول وقسم، وتسجيل كل تغيير في سجل تدقيق تلقائي.
  3. متابعة التأخير والعوائق: رصد المهام المتأخرة، أسبابها، واحتياجاتها (دعم/اعتماد/ميزانية/قرار).
  4. التعاون بين الأقسام: مهمة واحدة قد تشترك فيها عدة أقسام بأدوار مختلفة (تنفيذ/موافقة/دعم...).
  5. رؤية إدارية فورية: لوحة تحكم بمؤشرات ورسوم بيانية + تقارير جاهزة للطباعة والتصدير.
  6. تجربة استخدام احترافية: عربية كاملة، تصميم عصري، متوافق مع الجوال، وهوية بصرية مرنة.

3. المشكلة التي يحلّها

المشكلة قبل النظام الحل داخل النظام
تشتّت المهام في جداول Excel ورسائل منفصلة قاعدة بيانات مركزية واحدة + لوحة موحّدة
غياب المساءلة (من المسؤول؟) كل مهمة لها مسؤول + قسم رئيسي + أقسام معنية
عدم وضوح التأخيرات وأسبابها حقول تأخير + مؤشرات «متأخر؟» + تقرير تأخير مخصّص
صعوبة معرفة عبء كل موظف/قسم تقرير أداء الموظفين + تقرير الأقسام
لا يوجد سجل لمن غيّر ماذا ومتى سجل تدقيق تلقائي لكل تغيير
صعوبة إخراج تقارير للإدارة طباعة/PDF + تصدير Excel بنقرة

4. الفئات المستهدفة

الفئة الاستخدام الدور التقني
الإدارة العليا / مدير المشروع متابعة شاملة، تقارير، قرارات. admin / manager
مديرو الأقسام متابعة مهام أقسامهم وفرقهم. manager
الموظفون المنفّذون تنفيذ المهام المسندة إليهم وتحديث حالتها. user
مسؤول النظام (IT) إدارة المستخدمين والإعدادات والهوية. admin

5. الأدوار والصلاحيات

النظام يعتمد ثلاثة أدوار مخزّنة في عمود users.role، وتُطبَّق عبر Policies (ProjectPolicy, TaskPolicy) وcanAccess() في صفحات Filament.

الدور المشاريع المهام المستخدمون/الأقسام الإعدادات وسجل التدقيق التقارير
admin كامل كامل كامل كامل كل الأنواع
manager إنشاء/تعديل (حذف لما أنشأه) كامل عرض — كل الأنواع
user — مهامه والمرتبطة به فقط — — تقرير مهامه فقط

تفاصيل مهمة من الكود:

  • الوصول إلى اللوحة يتطلب is_active = true (عبر User::canAccessPanel()).
  • حذف مشروع: للأدمن أو منشئ المشروع فقط (ProjectPolicy::delete).
  • المستخدم العادي يرى مهمة إذا كان مسؤولها أو منشئها (TaskPolicy::view).
  • صفحة التقارير مفتوحة لكل مستخدم مسجّل، لكن user مقيّد بنطاق «مهامي» فقط.

6. الوحدات (Modules)

اللوحة مقسّمة إلى مجموعتين رئيسيتين في السايد بار، إضافةً إلى صفحات شخصية غير مجمّعة.

6.1 مجموعة «إدارة المشاريع»

الوحدة النوع الوصف
المشاريع (ProjectResource) Resource إدارة المشاريع الكاملة + علاقات (أعضاء، فرق، أقسام، مهام، ملفات).
المهام (TaskResource) Resource إدارة المهام + الأقسام المعنية + العوائق + التعليقات + المرفقات + السجل.
الفرق (TeamResource) Resource تكوين فرق العمل وربط الأعضاء والمشاريع.
لوحة المهام (KanbanBoard) Page كانبان: أعمدة الحالات وسحب المهام بينها.
التقويم (TasksCalendar) Page عرض المهام على تقويم حسب تاريخ الاستحقاق.

6.2 مجموعة «الإدارة والإعدادات»

الوحدة النوع الوصف
المستخدمون (UserResource) Resource إدارة المستخدمين، الأدوار، الأقسام، المدراء، التفعيل.
الأقسام (DepartmentResource) Resource الأقسام ومديروها وموظفوها ومهامها.
الإشعارات (NotificationResource) Resource إدارة الإشعارات (إداري).
التقارير (Reports) Page 5 تقارير + فلاتر ذكية + طباعة/تصدير.
سجل التدقيق (AuditLogResource) Resource عرض كل التغييرات (للأدمن).
إعدادات المظهر (ManageAppearance) Page الهوية: الاسم، الشعار، اللون، نمط السايد بار (للأدمن).
فريق التطوير (DevTeam) Page صفحة Quantum Dev Team.

6.3 صفحات شخصية (غير مجمّعة)

الصفحة الوصف

6.4 ودجات لوحة التحكم (Widgets)

الودجة العرض

8. المفاهيم والحالات الأساسية

حالات المشروع/المهمة (status)

pending قيد الانتظار · in_progress قيد التنفيذ · completed مكتمل · cancelled ملغى.

الأولوية (priority)

low منخفض · medium متوسط · high عالٍ · urgent عاجل.

مسؤولية القسم في المهمة (task_departments.responsibility)

primary مسؤول رئيسي · execution تنفيذ · financial قرار/اعتماد مالي · advisory استشاري · approval موافقة · support دعم.

خصائص محسوبة (Computed) مهمة

  • المهمة متأخرة (is_delayed): لها due_date ماضٍ وحالتها ليست مكتملة/ملغاة.
  • أيام التأخير (days_delayed): الفرق بين تاريخ الاستحقاق واليوم.
  • المهمة محجوبة (is_blocked): لها اعتمادية (Dependency) غير منجزة.
  • نسبة إنجاز المشروع (completion_rate): المهام المكتملة ÷ إجمالي المهام.

9. سير العمل داخل النظام (Workflows)

9.1 دورة حياة المهمة

إنشاء المهمة (pending)
   └─ إسناد لمسؤول + قسم رئيسي + أقسام معنية
        └─ بدء التنفيذ (in_progress) + تحديث نسبة الإنجاز
             ├─ تسجيل عوائق / أسباب تأخير عند الحاجة
             └─ اكتمال (completed) أو إلغاء (cancelled)

عند كل خطوة يسجّل TaskObserver نشاطًا في السجل الزمني ويُرسل إشعارات تلقائية (للمسؤول والمنشئ).

9.2 التعاون متعدد الأقسام

مهمة واحدة → قسم رئيسي (tasks.department_id) + عدة أقسام معنية (task_departments) لكلٍّ منها نوع مسؤولية. فلتر القسم في جدول المهام يجلب المهمة سواء كان القسم رئيسيًا أو معنيًا.

9.3 المتابعة والتقارير

الإدارة → لوحة التحكم (مؤشرات) → التقارير (فلترة بالنطاق/القسم/الحالة) → طباعة/PDF أو Excel

9.4 المساءلة (Audit)

أي إنشاء/تعديل/حذف على مشروع أو مهمة أو مستخدم أو قسم → AuditObserver يكتب سجلًا (من، ماذا، متى، وما الحقول التي تغيّرت).

10. لمحة معمارية سريعة

      → Resources / Pages / Widgets

1. تسجيل الدخول والخروج

  1. افتح https://<عنوان-النظام>/admin.
  2. أدخل البريد الإلكتروني وكلمة المرور.
  3. اضغط تسجيل الدخول.

🔑 المستخدمون الجدد يستلمون كلمة مرور أولية (123456 للموظفين المُنشَئين بالبذرة) ويُنصحون بتغييرها فورًا من الملف الشخصي.

الخروج: من القائمة أعلى يمين اللوحة (اسم المستخدم) ← تسجيل الخروج. عند الخروج تُمسح الفلاتر المحفوظة في الجلسة.

📸 لقطة: 01-login.png

2. لوحة التحكم

بعد الدخول تظهر لوحة التحكم وتحتوي على:

  • بطاقات المؤشرات (إجمالي المشاريع/المهام، المتأخرات...).
  • رسوم بيانية: حالة المشاريع، حالة المهام، المهام حسب الأولوية.
  • أحدث المهام: جدول بآخر المهام المُضافة.

📸 لقطة: 02-dashboard.png

3. إدارة المستخدمين

متاحة للأدمن. المسار: الإدارة والإعدادات ← المستخدمون.

إضافة مستخدم:

  1. اضغط جديد.
  2. عبّئ: الاسم، البريد، الهاتف، المسمّى الوظيفي.
  3. اختر القسم والمدير المباشر.
  4. اختر الدور (admin/manager/user) وحدّد نشط.
  5. أدخل كلمة مرور أولية ← حفظ.

تعديل/تعطيل: افتح المستخدم ← عدّل ← أزل «نشط» لمنع دخوله دون حذفه.

📸 لقطة: 03-users-list.png, 03b-user-form.png

4. إدارة الأقسام

المسار: الإدارة والإعدادات ← الأقسام.

  1. جديد ← أدخل اسم القسم (والرمز/الوصف اختياريًا).
  2. اختر مدير القسم.
  3. حفظ.

كل قسم يعرض موظفيه ومهامه المرتبطة. الأقسام الافتراضية: تقنية المعلومات، المالية، الموارد البشرية، المشاريع، الشؤون التعليمية، المرافق والخدمات العامة، الأمن والسلامة، النقل والحركة.

📸 لقطة: 04-departments.png

5. إدارة المشاريع

المسار: إدارة المشاريع ← المشاريع.

إنشاء مشروع:

  1. جديد.
  2. عبّئ: الاسم، الوصف، الحالة، الأولوية، نسبة الإنجاز، تاريخ البداية/النهاية.
  3. اختر مدير المشروع.
  4. حفظ.

داخل صفحة المشروع (Relation Managers): الأعضاء، الفرق، الأقسام المشاركة، المهام، والملفات.

مؤشر التأخير: إذا تجاوز المشروع تاريخ نهايته دون اكتمال يظهر «متأخر».

📸 لقطة: 05-projects-list.png, 05b-project-form.png

6. إدارة المهام

المسار: إدارة المشاريع ← المهام.

إنشاء مهمة:

  1. جديد.
  2. العنوان + الوصف.
  3. المشروع التابعة له.
  4. الحالة والأولوية ونسبة الإنجاز.
  5. المسؤول (المستخدم المكلَّف).
  6. القسم الرئيسي + الأقسام المعنية (لكل قسم نوع مسؤولية: رئيسي/تنفيذ/مالي/استشاري/موافقة/دعم).
  7. التواريخ (بداية/استحقاق) والساعات التقديرية/الفعلية.
  8. حقول التأخير (السبب + يحتاج: دعم/اعتماد/ميزانية/قرار) عند الحاجة.
  9. الملاحظات (اختياري).
  10. حفظ.

عرض مهمة (/admin/tasks/{id}): صفحة تفاصيل شاملة تعرض كل الحقول + التبويبات:

  • العوائق (Obstacles): نوع، وصف، الأثر، المسؤول، الحالة.
  • التعليقات (Comments): نقاش الفريق حول المهمة.
  • الملفات (Files): مرفقات المهمة.
  • السجل الزمني (Activities): كل ما جرى على المهمة (تلقائي).

الاعتماديات: يمكن ربط المهمة بمهام يجب إنهاؤها أولًا؛ إذا كانت إحداها غير منجزة تُعتبر المهمة محجوبة.

5. دورة البيانات داخل النظام (Data Lifecycle)

مثال: إنشاء مهمة وإسنادها

1. المستخدم يملأ نموذج المهمة في TaskResource::form()  (Livewire)
2. Filament يتحقّق من الحقول ثم يستدعي Task::create()
3. Eloquent يحفظ الصف في جدول tasks
4. تُطلق أحداث النموذج → تلتقطها المراقبات:
   ├─ TaskObserver::created()  → TaskActivity (سجل) + NotificationService::send() (إشعار للمسؤول)
   └─ AuditObserver::created() → AuditLog (تدقيق)
5. الأقسام المعنية تُحفظ في task_departments → TaskDepartmentObserver
6. عند التعديل: TaskObserver::updated() يرصد wasChanged('status'/'assigned_to') ويُشعر

مثال: عرض تقرير مفلتَر

Reports Page (Livewire) → getFilters() → ReportService::build($type,$filters)
   → applyTaskFilters() (scope/department/status) → استعلام Eloquent → صفوف
   → عرض في reports.blade / أو ReportController للطباعة/التصدير

6. أفضل الممارسات المتبعة

  • فصل الاهتمامات: منطق الأعمال في Services/Observers لا في Blade.
  • Idempotency: ProductionSeeder يستخدم firstOrCreate فيُعاد تشغيله بأمان.
  • الأمان أولًا: Policies + canAccess() + إخفاء الحقول الحساسة في التدقيق + تقييد المستخدم العادي بنطاقه.
  • مصدر واحد للحقيقة للهوية: جدول settings يقود المظهر بالكامل.
  • منع N+1: استخدام with() في استعلامات التقارير والجداول.
  • التوطين: كل النصوص عبر resources/lang/ar.json وثوابت عربية في الموارد.

1. ملخّص الحالة

النظام تطبيق لوحة تحكم (Server-rendered) مبني على Filament + Livewire. لا توجد حاليًا واجهة REST API عامة موجّهة لمستهلكين خارجيين. التفاعل يتم عبر:

  1. لوحة Filament على /admin/* — عبر جلسة مصادَقة (Livewire يتبادل الحالة داخليًا).
  2. مساري تقارير HTTP عامّين (يتطلبان جلسة مسجّلة): الطباعة والتصدير.
  • routes/api.php: لا مسارات مخصّصة (الملف الافتراضي).
  • laravel/sanctum مُثبّت (يوفّر أساسًا جاهزًا لبناء API موثّق برموز عند الحاجة).

هذا المستند يوثّق المسارات الفعلية المتاحة بدقّة، ثم يشرح كيفية إضافة API رسمي.

4. النشر على Railway (الطريقة المعتمدة)

النظام منشور على Railway باستخدام Nixpacks. الملفات الثلاثة التي تحكم النشر:

4.1 railway.toml

[build]
builder = "NIXPACKS"

[deploy]
startCommand = "/bin/bash railway-start.sh"

4.2 nixpacks.toml

  • setup: يثبّت php82 + إضافات intl/zip/gd + composer (لأن تعريف nixPkgs يستبدل الافتراضي).
  • install: composer install --no-dev --optimize-autoloader --ignore-platform-reqs.
  • build: لا بناء واجهة أمامية (Filament مُجمَّع مسبقًا) — يتجاوز npm.

4.3 railway-start.sh (سكربت الإقلاع المرن)

منطق الإقلاع خطوة بخطوة:

  1. انتظار قاعدة البيانات: حتى DB_WAIT_ATTEMPTS محاولة (فحص اتصال PDO فعلي) مع sleep.
  2. عند الجاهزية: migrate --force (أو migrate:fresh إذا DB_FRESH=1) ثم db:seed --class=ProductionSeeder --force.
  3. إذا لم تجهز القاعدة: يبدأ التطبيق بدون ترحيل (يبقى Online بدل إسقاط الحاوية).
  4. دائمًا: storage:link + filament:assets + config:cache + route:cache + view:cache.
  5. exec php artisan serve --host=0.0.0.0 --port=$PORT.

4.4 خطوات النشر

  1. اربط مستودع GitHub بمشروع Railway.
  2. أضِف خدمة MySQL في Railway وانسخ متغيّراتها.
  3. اضبط متغيّرات البيئة (القسم 2) في إعدادات الخدمة.
  4. ادفع إلى فرع main → Railway يبني وينشر تلقائيًا.
  5. تابع سجلّات الإقلاع (==> [startup] ...) للتأكد من الترحيل والبذر.

5. HTTPS وروابط الأصول

خلف وكيل Railway (TLS إنهاء عند الحافة)، تُمرَّر الطلبات كـ HTTP داخليًا. لذلك:

  • app/Http/Middleware/TrustProxies.php يضبط $proxies = '*' حتى تولّد Laravel روابط https:// صحيحة للأصول (وإلا تُحجب لمحتوى مختلط).
  • filament:assets في الإقلاع يضمن مطابقة الأصول لإصدار الحزمة.

إذا ظهرت الواجهة بلا تنسيق: تحقّق من APP_URL=https://...، ونفّذ filament:assets + storage:link، وأعد النشر.

6. أول نشر / إعادة تعيين لمرة واحدة

  • قاعدة نظيفة أول مرة: اضبط DB_FRESH=1 لنشرة واحدة ثم أزِله فورًا (وإلا سيمسح البيانات في كل نشر).
  • بعد ذلك يعمل migrate --force بشكل تراكمي وProductionSeeder بشكل idempotent — إعادة النشر لا تمسح تعديلات المستخدمين.

7. ما بعد النشر — قائمة تحقّق

  • فتح /admin وتسجيل الدخول بالأدمن.
  • ظهور الواجهة بتنسيق كامل (CSS/JS).
  • ظهور المستخدمين الـ7 والمشروع والمهام (من البذرة).
  • رفع صورة في الملف الشخصي يعمل (تأكيد storage:link).
  • الطباعة/التصدير في التقارير تعمل.
  • الشعار الكبير يظهر في صفحة الدخول.

1. النمط المعماري

النظام يتّبع نمط Server-Driven UI عبر Filament + Livewire فوق معمارية Laravel الطبقية (MVC موسّعة بالخدمات والمراقبات). لا توجد واجهة أمامية منفصلة (SPA)؛ الواجهة تُبنى على الخادم وتُحدَّث تفاعليًا عبر Livewire.

الطبقات:

Presentation  →  Filament (Resources / Pages / Widgets) + Blade
Authorization →  Policies + canAccess()
Domain        →  Models (Eloquent) + خصائص محسوبة
Reactions     →  Observers (Audit / Task / Comment / Department)
Services      →  NotificationService / ReportService
Persistence   →  Eloquent ORM → MySQL
